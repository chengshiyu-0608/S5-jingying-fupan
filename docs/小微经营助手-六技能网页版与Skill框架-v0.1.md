# 小微经营助手｜六技能网页版与 Skill 框架

版本：v0.1  
日期：2026-09-30  
定位：先做六个可独立使用、可独立回归的精品 Skill；稳定后再组合成“小微经营专家”。

## 1. 总体产品结构

```text
小微经营者工作台
├── 生意方向与选品
├── 成本与定价
├── 选址与合规
├── 采购与库存
├── 获客与成交
└── 经营复盘与复购
        ↓
   小微经营专家（后续组合）
```

六个技能先各自拥有：

- 一个独立 Skill 包；
- 一个独立网页版入口；
- 一套确认卡字段；
- 一套输入材料和输出物；
- 一套回归样本；
- 一套质量指标。

后续专家只做路由和跨模块上下文传递，不复制六个技能的正文。

## 2. 六个独立 Skill 的边界

| 编号 | Skill 名称 | 解决的问题 | 首期 3 个精品事项 | 明确不做 |
|---|---|---|---|---|
| S1 | 生意方向与选品 | 做什么、卖给谁、先验证什么 | 经营方向判断、主卖品筛选、菜单结构 | 长期战略、融资计划、泛品牌策划 |
| S2 | 成本与定价 | 单品花多少钱、卖多少钱不亏 | 单品成本、定价保本、套餐测算 | 财务报表代记、税务结论、投融资估值 |
| S3 | 选址与合规 | 哪个点值得去看、要确认哪些规则 | 候选点比较、人流观察、材料清单 | 保证审批、法律结论、虚构实时客流 |
| S4 | 采购与库存 | 买什么、买多少、如何减少损耗 | 供应商比价、首日备货、损耗补货 | 自动下单、供应商背书、库存系统替代 |
| S5 | 获客与成交 | 让顾客看懂、停留并完成选择 | 门头菜单、开业预告、现场成交 | 短视频全链路、自动发布、收入保证 |
| S6 | 经营复盘与复购 | 今天发生了什么、明天只改什么 | 每日经营记录、明天改一件事、复购方案 | 复杂 CRM、长期收入预测、强制收集隐私 |

### 2.1 模块之间的连接

默认业务路线：

```text
方向与选品 → 成本与定价 → 选址与合规 → 采购与库存
→ 获客与成交 → 经营复盘与复购 → 回到选品/定价/选址调整
```

路线是推荐顺序，不是强制流程。用户已有可靠结果时，可以跳过节点。

## 3. 每个 Skill 包的统一目录

```text
guiputi-business-<module>/
├── SKILL.md
├── VERSION
├── CHANGELOG.md
├── agents/openai.yaml
├── references/
│   ├── intent-card.md       # 确认卡字段与用户必须拍板项
│   ├── scene-map.md         # 3 个精品事项和场景边界
│   ├── output-schema.md      # 输出物结构和完成标准
│   ├── guardrails.md         # 事实、风险、材料闸门
│   └── regression.md         # 正向样本、诱饵、验收词
└── web/
    ├── index.html            # 独立网页版入口
    └── README.md             # 本网页与 Skill 的字段映射
```

`SKILL.md` 只放路由、原则和必要流程；详细字段、样本和输出规范放到 `references/`，避免六个包互相复制。

## 4. Skill 的统一执行协议

所有需要“写、算、比较、规划、生成、发布”的请求，都遵循：

```text
用户问题
  ↓
match_scene
  ↓
get_scene_form
  ↓
确认卡：目标 / 经营对象 / 阶段 / 材料 / 交付物 / 边界
  ↓
用户填写或点选
  ↓
submit_fields
  ↓
confirm_intent
  ↓
材料闸门：缺必需材料就停止编译
  ↓
compile_task
  ↓
按 protocol_prompt 生成输出物
  ↓
report(completed)
```

### 4.1 确认卡统一字段

每个 Skill 可按场景增删，但至少保留：

| 字段 | 说明 | 来源 |
|---|---|---|
| `business_form` | 流动摊位、固定摊位、小门店、线上/上门 | 用户确认 |
| `business_type` | 小吃、饮品、零售、生活服务等 | 用户确认 |
| `stage` | 准备、试营业、稳定经营、调整 | 用户确认 |
| `goal` | 当前要解决的一个问题 | 用户确认 |
| `facts` | 用户已经提供的事实和数据 | 用户材料 |
| `materials` | 文件、照片、记录、链接或截图 | 用户材料 |
| `assumptions` | AI 为了继续工作提出的假设 | AI，必须标记 |
| `deliverable` | 本次要生成的结果 | 用户确认 |
| `done_rule` | 什么算完成 | 用户确认或 AI 建议 |

必须用户拍板的内容最多 3 项；AI 可以补充的内容不能伪装成用户事实。

### 4.2 统一材料闸门

- 没有数据时先给“待补材料清单”，不编造经营结果；
- 服务端返回 `material_missing` 时，必须说明缺少的材料；
- 用户明确允许估算时，估算值必须单独标注；
- 证照、食品、消防、摊位规则以当地官方最新要求为准；
- 花钱、对外发送、提交、发布前必须再次确认。

## 5. 每个网页的统一产品骨架

网页版不是单纯把 Skill 文本放在页面上，而是一个“任务工作台”。参考 Notion 的结构化工作区和 RunningHub 的任务卡/工作流入口，但界面和内容使用硅菩提自己的设计与文案。

### 5.1 页面层级

```text
独立 Skill 网页
├── 首页 / 任务入口
│   ├── 一句话定位
│   ├── 3 个精品任务卡
│   ├── 适用经营形态
│   └── 最近一次任务
├── 开始任务
│   ├── 场景选择
│   ├── 确认卡
│   ├── 材料上传/粘贴
│   └── 用户确认
├── 结果工作区
│   ├── 行动卡或成品
│   ├── 已确认事实
│   ├── AI 假设
│   ├── 完成标准
│   └── 下一步任务
├── 经营记录
└── 我的材料
```

### 5.2 单技能网页的固定状态

```text
idle → selecting → confirming → material_check
→ generating → result → completed
```

异常状态：

- `need_materials`：缺材料，显示缺口和补交入口；
- `need_clarification`：有分歧，回到确认卡；
- `connector_unavailable`：确认卡连接器不可用，不伪造卡片；
- `draft_only`：用户明确允许先出估算草稿，必须标注假设。

### 5.3 结果页固定结构

每个技能的结果页都要显示：

1. 本次任务；
2. 用户确认的事实；
3. AI 假设；
4. 结果或行动卡；
5. 完成标准；
6. 风险和限制；
7. 下一步技能；
8. 保存、复制、重新确认。

## 6. 六个网页的差异化设计

共享布局和确认卡协议不变，只替换任务卡、字段和结果组件。

| Skill | 首页主文案 | 核心输入 | 核心结果组件 |
|---|---|---|---|
| S1 方向选品 | 先确定值得试卖的方向 | 想法、客群、品类、预算、限制 | 经营假设卡、候选品比较表、验证动作 |
| S2 成本定价 | 先算清，再决定卖多少钱 | 原料、包装、损耗、售价、销量 | 成本拆分表、毛利/保本计算、情景比较 |
| S3 选址合规 | 先看事实，再决定要不要去 | 地址、时段、人流、竞品、地区 | 候选点比较表、现场观察表、官方材料清单 |
| S4 采购库存 | 买得少一点，卖得稳一点 | 供应商、报价、销量、保质期、补货时间 | 报价比较、首日备货表、损耗行动卡 |
| S5 获客成交 | 让路人一眼看懂并愿意选择 | 品名、价格、卖点、地点、时段 | 门头/菜单结构、开业预告、现场话术 |
| S6 复盘复购 | 收摊后只决定下一件事 | 销量、营业额、成本、客单、反馈、复购 | 经营记录、下一步动作、复购方案 |

## 7. 质量标准：Skill 和网页必须一起验收

### 7.1 Skill 质量门槛

- 触发边界清楚，不吸引不相关请求；
- 3 个事项各自有明确输入、输出和完成标准；
- 每个事项都先走确认卡；
- 必需材料缺失时能停在材料闸门；
- 用户事实、AI 假设和计算结果分开；
- 至少 3 条回归样本：2 条正向、1 条诱饵；
- 事项召回位次进入前 2，优先冲第 1；
- 不虚构政策、客流、销量、审批或收入；
- 成品结构、格式规范和常办事项数量一致。

### 7.2 网页质量门槛

- 用户 30 秒内能理解该 Skill 解决什么问题；
- 从首页到确认卡不超过 2 次点击；
- 表单未填完时不能确认；
- 确认前不生成最终结果；
- 缺材料时能回到材料补交状态；
- 结果页能看到事实、假设、完成标准和下一步；
- 刷新后保留当前任务和最近记录；
- 主要按钮、空状态、加载状态和错误状态都有反馈；
- 移动端和桌面端都可用；
- 每个网页可独立演示，不依赖专家总入口。

## 8. 开发顺序

产品路线顺序和开发顺序不完全相同。

### 建议的开发顺序

1. **S2 成本与定价**：输入输出最容易客观校验，先验证确认卡、材料闸门和计算结果。
2. **S1 生意方向与选品**：验证开放式问题的确认卡和候选方案质量。
3. **S6 经营复盘与复购**：建立真实记录和后续动作闭环。
4. **S4 采购与库存**：复用成本字段和经营记录。
5. **S3 选址与合规**：风险最高，最后接入官方入口和地区差异。
6. **S5 获客与成交**：明确不覆盖短视频全链路，聚焦线下物料和成交。
7. **组合专家**：六个 Skill 全部通过回归后再合并路由。

### 每个 Skill 的制作周期

```text
业务边界 → 可复用方法审阅 → 场景/字段设计
→ 确认卡协议 → Skill 初版 → 网页原型
→ 本机走通 → 回归样本 → 质量修正 → 独立包验收
```

每完成一个 Skill，才进入下一个；不要六个一起半成品并行。

## 9. 组合成专家的规则

六个 Skill 合成专家时：

- 专家只保留一个统一入口和六个模块路由；
- 各 Skill 的事项名称和 `scene_id` 不随合并改变；
- 专家共享经营画像、材料库和最近动作；
- 专家根据阶段、目标和已完成节点推荐下一 Skill；
- 同一用户问题只能由一个主 Skill 负责，避免多个事项抢召回；
- 每个 Skill 的独立网页继续保留，专家页只是总入口。

- 在没有发布中心查重和回归证据前提交上架。
